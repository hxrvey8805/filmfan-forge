CineGeek in-app password recovery — 23 November 2026

Outcome
The owner wants password changes inside the iPhone app and declined buying a
domain. The approved existing host, cinegeek.lovable.app, remains the HTTPS return
address. This revision uses the existing Supabase recovery email unchanged; no
custom sender, paid email product, domain purchase, migration or auth setting is
required. The earlier prepared custom email template is NOT used by this rollout.

Implementation
- iOS requests use a dedicated Supabase PKCE client with separate persisted storage.
  An S256 verifier stays on the requesting phone. A random request state and expiry
  bind the return to that request; email addresses are not stored in its marker.
- The ordinary login client, signup flow and account session remain separate.
- The existing email returns to /reset-password?app=1&state=...&code=... .
  The browser does not exchange this code or import an implicit session. It scrubs
  the query and shows an Open CineGeek button if iOS did not open the app directly.
- The button uses app.cinegeek.mobile://reset-password with only the code and
  request state. No access token, refresh token or recovery hash is accepted on
  that scheme. Intercepting the code cannot exchange it without the S256 verifier.
- HTTPS Universal Links remain limited to the existing host and /reset-password;
  AASA binds RAG9TBP6L8.app.cinegeek.mobile. Family Controls permissions are preserved.
- A Continue tap exchanges the code in the requesting app. getUser verifies the
  returned account before showing password fields and again before updateUser.
  Newer links and cancellation invalidate pending results and stale forms.
- After completion, temporary and current local sessions end for fresh sign-in.
  Legacy browser recovery remains supported. No automatic worker update/reload is
  registered on reset/auth routes. Capacitor payload logging remains disabled.
- The same iPhone must request and finish the reset. A reinstall, another device,
  old/reused email or unavailable verifier requires a fresh in-app request. Email
  clients and user link preferences may still show a brief browser handoff.

Validation
