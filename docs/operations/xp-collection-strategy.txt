CineGeek XP collection strategy — 27 November 2026

Status: implemented and locally verified; not merged, deployed or uploaded to TestFlight.
Branch: feat/xp-collection-strategy-2026-11-27
Base: origin/main 710fcac

Behaviour
- Monthly: 750 XP for one random unowned skin. No specific-skin purchases.
- Free retains the default Geek. Annual still includes every skin.
- Card packs remain 150 XP. Capacity remains six actors and six directors.
- Empty-slot acceptance and skipping a reveal cost no additional XP.
- Only a full same-type shelf can replace a card: 450 XP extra, explicitly
  displayed and confirmed by the replacement button. No standalone removal,
  selling, XP refund, early replacement or cross-shelf replacement.
- Insufficient XP preserves both the existing card and the pending reveal.
- A lost response retains the exact choice across closing/reopening. Receipts
  prevent repeat charges. Cards, existing skins and historic receipts remain intact.

Server implementation
Apply supabase/migrations/20261127120000_xp_collection_strategy.sql once.
Wallet locking serializes debit, card replacement and receipt in one transaction.
The new decide_cinegeek_pack_v2 RPC requires explicit expected cost. The older
RPC retains historical receipt reads and free keep/skip, but refuses new swaps
with an update instruction rather than charging clients that do not show 450 XP.
The new user_packs replacement_xp_cost column defaults to zero for old decisions.
Direct client INSERT/UPDATE/DELETE remains revoked. Sell endpoints remain retired.
Generated Supabase types are unchanged; reviewed contracts live in tier-rpc.ts.

Rollout preparation
1. Deploy the migration before distributing the updated client. Do not restore
   the old free-replacement function or enable real purchases.
2. Run docs/operations/packs-skin-live-checks.sql. It uses disposable fixtures
   and rolls back all fixture rows, including skin and replacement debits.
3. Verify the existing production-sales flag remains false before and after.
4. Publish the matching client / prepare its next TestFlight build when requested.
   No TestFlight build number has been changed here.
5. If rollout fails, stop rather than release a client with mismatched prices.
   Preserve completed receipts; do not refund or rewrite historical transactions.
